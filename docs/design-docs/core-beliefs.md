# 核心信念

本文记录尽量保持稳定的设计信念。

## 1. 仓库是一个系统，不是一堆文件

任何修改都应尽量保持以下层次清晰：

- 路由协议
- shell 运行时
- 可复用组件
- 示例页
- 文档系统

## 2. `AGENTS.md` 是地图，不是手册全集

它应帮助读者找到正确知识，而不是试图把所有知识都塞进去。

## 3. `docs/` 是文档记录系统

长期有效的推理应放在 `docs/` 下的聚焦文档中。

## 4. 渐进披露优于上下文倾倒

无论是人还是智能体，都应从一个小而稳定的入口开始，再按主题逐层深入。

## 5. Route Metadata 应驱动 Shell 行为

布局、菜单、标签页、keep-alive 等 shell 行为，只要可能，就通过路由协议表达。

## 6. 共享组件是“产品”，不是一次性示例

`ProForm`、`ProTable`、`ProDialog`、`ProDetail`、`SearchBar` 都不是临时演示，它们的 API 应该被认真设计、文档化和测试化。

## 7. 示例页应验证复用，而不是积累业务逻辑

页面首先是示例面和验证面；如果承载了越来越多真实行为，这些行为就应下沉到可复用层。

## 8. 文档必须跟随运行时事实

当文档与代码不一致时，短期内以代码和测试为准；但文档仍应补齐。

## 9. 计划是一级工件

执行计划、债务记录和 follow-up 都应进入版本库，让仓库本身具备可持续的工作记忆。

## 10. 小而准确的系统，优于大而空泛的系统

不要为仓库里尚不存在的能力编写“想象中的文档”。
